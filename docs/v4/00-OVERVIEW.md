# Parhelion 4.0 概要设计

> 状态：已批准实施 · 适用版本：4.0.0 · 详细设计索引：[10-DETAILED-INDEX.md](10-DETAILED-INDEX.md)

## 1. 为什么要做 4.0

4.0 不加新功能面，而是把平台从"多 Agent 互相争抢"改回"少量 Agent 高效迭代"。依据是 2026-11-24 至 11-25 两场比赛的日志。

| 指标 | 第一场（10 题） | 第二场 3.4 之前（03:00–07:30Z） | 第二场 3.4–3.6.2（07:30–18:00Z） |
|---|---|---|---|
| 并发 Agent | 每题 1–3 个，人工派发 | 少量 | 42 个 DeepSeek 常驻 worker |
| 已通过题目的优化增益 | 最好一天 +181 分 / 117 发 | 约 +33 分 / 4.5h | +24 分 / 10.5h |
| 单次验证端到端 | 中位 80s，p90 281s | 中位 171–460s | 中位 260s，p90 2344s |
| 本地测速 | 每个桶都有 profiler 任务时长 | 只计时 perf 标记例 | 89% 用例不计时；首样本冷启动约 550µs，官方约 9µs |
| 突破记录的证据 | 33 条，全部附逐桶提速表 | — | 6 条，全部没有提速表 |
| token | — | — | 17,247 次模型调用，累计重读上下文约 23.6 亿 token，余额两次耗尽 |

### 1.1 根因

1. **测试工具调用会阻塞。** `parhelion_test_plan` 同步等待 `opsb test` 跑完，而 Harness 端的工具超时是 60 秒。604 次调用里 320 次超时。stdio MCP 服务按行串行转发请求，所以 status、squad、inbox 也排在后面跟着超时（69 + 33 + 12 次）。worker 超时后重试，制造了 133 个重复 run；还有 157 个 run（32%）停在 `built`，从没拿到设备。
2. **设备靠抢锁调度。** 通过调度器的 run 每批实际持锁中位数只有 4 秒，14 小时累计用设备 0.37 小时（约 3%）；但编译后等设备的 p90 是 38 分钟。原因是 3.6.2 之前 worker 直接 `ssh` + `flock` 抢锁，选出的队首又和内核里阻塞等锁的进程竞争，再加上孤儿进程和重复 run 抢同一把锁。
3. **本地测速没有信号。** 当前 case bench 用设备事件计时，第一个样本是冷启动；89% 的用例默认不计时；`timing_score_eligible` 恒为 false。worker 只好用官方提交来测速，进步速度被提交额度卡住。
4. **上下文只增不减。** DSH 报告的窗口是 100 万 token，压缩阈值却是 60% 窗口，实际永远不会触发；worker 上下文平均峰值约 22 万 token。工具输出里 43% 是读文件，`kb_query` 每次约 40KB，`status` 每次约 13KB。余额耗尽后又派出 149 条 followup，产生 265 次失败。
5. **协作接口和提示词对不上。** `parhelion_squad` 只接受 agent_id，提示词却写"发给 optimizer"，造成 122 次报错。每题 3 个席位，其中常驻的校准席位消耗了约三分之一 token，产出的 229 个实验 run 大多卡在排队里。
6. **污染。** pytest 往真实的 `~/.parhelion/workspaces` 写了 133 个 `ws-*` / `bus.db-*` 目录；网关日志每次刷新都写一行，`feedback-log.jsonl` 里有 43,039 条 gate 记录（16MB）；远端 `/tmp/opsb-npu-tickets` 遗留了 23 个死票。

### 1.2 要保留的成功经验

- **第一场的测速协议**：profiler 单会话、warmup 2、repeat 5、按桶取任务时长，并记录 launch floor、公开 tbest 锚点和隐藏层先验。
- **第二场 case bench 的长处**：用例从官方模板生成、oracle 冻结、相同输入可配对、每次运行留有不可变记录。
- **少量 Agent、短迭代**：3.4 之前 4.5 小时 +33 分。
- **已经验证有效的约束**：3.6.2 的 worker SSH 沙箱生效后，直接 `ssh` 调用全部被拒（65 次 denied）；按 (SHA, 配置) 共享同一结果的 `active_bench`。

## 2. 设计原则

1. **平台持有测量尺子。** 每题一个测试套件，由平台版本化管理；worker 只能选择强度级别，不能自建配置。
2. **一次运行只占一次设备。** 编译、准备输入和期望输出、比对都在 CPU 上做；设备时间只花在执行和计时上。
3. **工具调用不阻塞。** 任何可能超过 5 秒的操作都返回句柄，再用带上限的等待去取结果。
4. **上下文以 token 数为预算。** 按绝对 token 数控制压缩，不按百分比；需要时开新会话，并带上一张平台生成的状态卡。
5. **故障先熔断再通知。** 供应商余额或配额故障只上报一次，并暂停该驱动的所有派发。
6. **少即是多。** 默认每题 1 个 worker；需要助手或校准时显式开启。

## 3. 目标架构

```
┌──────────── Harness 层（DSH / Codex / Claude / Pi …）────────────┐
│ worker 会话：状态卡（≤2KB） + 精简 brief（≤1.5KB）                  │
└───────────────┬──────────────────────────────────────────────────┘
                │ MCP（stdio，多线程分发；回复可乱序）
┌───────────────▼──────────── 控制面（daemon）──────────────────────┐
│ ① 测试运行登记表 test_runs  ② 编排器 AgentMesh（熔断/压缩/投递）  │
│ ③ 状态卡生成  ④ 提交网关（不变）  ⑤ 总线（squad 按角色寻址）        │
└───────────────┬──────────────────────────────────────────────────┘
                │ opsb test --level …（后台进程，结果写 report.json）
┌───────────────▼──────────── 测试平台（scheduler）─────────────────┐
│ 统一套件 suite.json（case 是最小单元，桶是标签，带权重/计时标记）   │
│ 级别 smoke / standard / final → 选例、计时协议、去重键                │
│ 报告：逐例判定 + 逐桶热态耗时 + 公开例预计分 + 相对基线变化          │
└───────────────┬──────────────────────────────────────────────────┘
                │ ssh（只有 daemon 和 opsb 可用）
┌───────────────▼──────────── 设备主机 ────────────────────────────┐
│ 设备代理 device_broker：单进程按 WSPT 顺序执行作业，持有设备锁，    │
│ 强制单作业超时，写探针可见的会话与账本记录                           │
│ case_batch：CPU 侧准备与比对；热态计时（丢弃 warmup，取 min/median）│
└──────────────────────────────────────────────────────────────────┘
```

### 3.1 测试平台：统一套件与级别

- **用例（case）是最小单元。** 每个用例带这些属性：来源（official / local）、所属桶、分数权重、是否计时。桶只是用例上的标签，不再单独维护一套东西。
- **级别**：
  - `smoke`：只跑失败重测例、一个正确性锚点和一个计时例，用于改完代码快速自查；
  - `standard`：全部正确性例，加上所有计时例的热态测速，作为日常迭代和提交前的依据；
  - `final`：在 standard 之外，增加所有 local 对抗例和更多重复次数，只给提交候选跑一次。
- **计时协议**：计时例先跑 warmup 次（默认 2，丢弃），再跑 repeats 次（默认 5），报告最小值、中位数和冷启动样本。达到 warmup≥1、repeats≥3 时，`timing_score_eligible = true`。
- **报告**：逐例判定；逐桶热态耗时；基于最新官方 `public_tbest_us` 的公开例预计分；如果有同套件版本的基线报告，再给出逐例、逐桶的相对变化。
- **去重**：去重键为 (题目, SHA, 套件版本, 级别, 设备环境)。相同请求加入正在进行的运行，或复用 30 分钟内的已完成结果。

### 3.2 设备代理

- 设备主机上只有一个常驻代理进程执行设备作业，作业通过本机 unix socket 提交。
- 代理按 (tier, WSPT 优先级, 创建时间) 出队，一次只执行一个作业，作业期间持有原有的设备锁文件，这样不经过平台的工具也会被拦在外面。
- 单作业有总超时，超时就杀掉样例进程，并对剩余用例返回 TLE，不再重新排队。
- 代理按原格式写 `die_session.json`、`die_ledger.jsonl` 和票据记录，现有探针和 UI 不需要改动。
- 启动时清理死票。代理崩溃或不可用时，回退到 3.6.2 的车道逻辑，并在报告里标注 `broker: false`。

### 3.3 控制面

- **MCP 服务**：stdio 收到请求后分发到线程，回复带锁写出，可以乱序返回，长调用不再挡住其他请求。
- **测试工具**：
  - `parhelion_test` 提交测试，2 秒内返回 `run_id`；
  - `parhelion_test_wait` 最多等待 45 秒，返回进度或精简结果；
  - `parhelion_test_plan` 保留为兼容别名，`execute=true` 时等价于先提交、再等待 40 秒。
- **完成投递**：运行结束后，编排器把精简结果作为 `test_result` 消息投到请求者的收件箱；worker 空闲时唤醒它。
- **工具输出上限**：`status` 默认不超过 2KB；`kb_query` 默认 top 3、每条摘要不超过 600 字符；需要完整内容时显式传 `full=true`。

### 3.4 编排与 token 经济

- **默认每题 1 个 worker**（`solo`）。`algorithm` / `dataflow` 双轨和校准席位改为显式选项。
- **供应商故障熔断**：错误文本匹配余额、配额、401/402/429 时，把该驱动标记为 `suspended`；停止向它的所有 worker 派发 followup；只发一条 strategic 告警。管理员恢复后才解除。
- **压缩阈值**：默认 12 万 token，可配置。达到阈值后，在阶段结果后开新会话，只带状态卡和阶段结论。
- **状态卡**：不超过 2KB，由平台根据账本生成，内容包括当前最佳 SHA 和分数、HEAD、公开例与 tbest 的差距、最近 3 次测试摘要、最近 3 次官方回执、套件版本，以及禁用直连设备的规则。
- **brief**：精简到 1.5KB 以内，工具名和角色名与 MCP 契约一致。
- **squad 寻址**：接受 agent_id、角色名（axis / role_label）或 `all`；出错时直接返回队友列表。

### 3.5 去掉的污染与 bug

- conftest 把 `PARHELION_HOME` 指向会话级临时目录。
- 网关日志只在判定变化时写入。
- 新增 `opsb doctor --clean`：清理被测试污染的工作区目录；在远端清理死票。
- 不再给 `error` / `stopped` 状态的 worker 派发消息。

## 5. 验收指标

| 指标 | 3.6.2 实测 | 4.0 目标 |
|---|---|---|
| `parhelion_test` 返回时间 | 60s 超时 | ≤ 2s |
| 测试工具超时率 | 53% | 0（等待调用自带上限） |
| 重复 run 比例 | 27% | < 5% |
| 设备等待 p90（单题、无争用） | 2324s | ≤ 60s |
| 计时用例比例（standard） | 11% | 100% 的 perf/计时例 |
| 本地热态与官方的偏差 | 冷样本约 60 倍 | ≤ 5%（以 NeighborList 01 为参照） |
| 单个 worker 上下文峰值 | 约 22 万 token | ≤ 12 万 token |
| 供应商故障后的失败次数 | 265 | ≤ 每个 worker 1 次 |

## 6. 不在 4.0 范围内（4.1 路线）

- profiler 任务时长接入 reference 引擎（4.0 先用热态事件计时，误差在 4% 以内）。
- A/B 交替配对（4.0 先用同套件版本的基线报告比较）。
- 跨题合并设备批次。
- Swift UI 的新卡片样式（4.0 只保证解码兼容）。
