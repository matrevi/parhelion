# Parhelion 4.2：上下文经济与压缩记忆

4.2 解决两件事。第一，worker 和主控把大量 token 花在平台本来就知道的东西上。第二，压缩之后会忘掉已经得到的结论，例如「某处可以优化」「某个方向已经证伪」。两件事的出路相同：把状态放到平台上，上下文里只放最有用的部分。

依据有三份：

- 2026-11-26 冲刺的实测，见 `docs/v4/RUN-LOG-2026-11-26.md`；
- 节约 token 的调研：Reasonix、Antigravity、提示缓存与工具输出，见 `research/token-economy.md`；
- 压缩与记忆的论文和社区方案，见 `research/compaction-memory.md`。

两份调研都标注了哪些数字读自原文、哪些未核实。

## 1. 实测：token 花在哪里

数据来自 2026-11-26 六题冲刺：13 个新 worker、1 个 DSH 主控，约 1 小时。

| 项目 | 数据 |
|---|---|
| worker 上下文峰值 | 中位 349K token，最高 422K；共压缩 17 次 |
| worker 起步上下文 | 中位约 10K，最高 44K，主要来自第一次平台调用之前的 `read`、`cd`、`ls` |
| 以 `cd` 开头的 shell 组合命令 | 1,766 次，返回 4.4MB。其中 `sed` 954KB、`git` 857KB、`python3` 594KB、`grep` 501KB、`ls` 318KB、`cat` 288KB |
| 临时 Python 脚本 | 621 个。388 个读 JSON，165 个直接解析 `report.json` 求逐例时间 |
| 绕过 MCP 直接用 CLI | `opsb queue list` 53 次，`opsb history` 约 30 次，`opsb bench verify-escape` 14 次 |
| 主控轮询 | `agent_wait` 约 250 次、`test_wait` 约 200 次、`agent_send` 约 200 次、`status` 约 110 次 |
| 总线消息 | `result` 317 条共 723KB，`peer` 198 条共 371KB，单条最长 7KB |
| 压缩后的重复劳动 | 1,036 次读文件中有 170 次（16%）读的是压缩前已经读过的文件；224 次测试请求中有 11 次重测压缩前测过的 SHA 和级别；没有一次复用已有运行 |

**结论**：浪费主要不在推理，而在 worker 反复推导平台已经掌握的信息，包括逐例对比、队列、历史和文件内容。压缩丢掉的是只存在于对话里的结论。

**另一个边界问题**：有 worker 在自己的工作树里直接导入平台内部模块，用 `board_refresh_service._all_team_sessions()` 读出全队判题账号的会话 cookie，再去查排行榜。worker 能拿到平台内部实现和凭据，这件事与 token 无关，但一并在 4.2 处理（工作包 K）。

## 2. 现在的压缩为什么会忘

代码位置：`cli/opsb_core/agents/manager.py`（`_checkpoint`、`_compact`）和 `cli/opsb_core/agents/adapters.py`。

- **ACP worker 的流程**：平台先让模型写一段「short handoff」，再新开一个会话，种入这段摘要和一个不超过 4,000 字符的 checkpoint（上一阶段结果加状态卡），最后一句是「Do not re-read files you already summarized」。
  - 「short」会诱导模型过度压缩。
  - 摘要由一个已有约 350K 上下文的模型来写，而中间段落最容易被忽略。
  - 没有任何结构强制列出待验证的假设和已证伪的方向。
- **checkpoint 截断的是阶段结果的结尾。** `_checkpoint` 取 `stage[:room]`，保留开头、丢掉结尾，而结论通常写在结尾。
- **摘要会逐代衰减。** 下一次压缩是在上一次摘要的基础上再压缩。调研中，三轮级联压缩后事实只剩 36.8%，完整上下文下是 90.1%（arXiv 2605.24657）；五轮后安全规则只剩 10%（2608.22752）。
- **Codex 的原生压缩保留最近的用户消息，丢掉助手推理。** 结果是同伴发来的长消息留下来了，worker 自己的洞见反而没了。
- **调研的共同结论**：状态写在磁盘上时，压缩阈值几乎无影响；丢失的都是只在对话里出现过的东西。LLM 摘要比直接遮蔽旧观察多花 24–94% 的 token，质量并不更好（2605.18854）。遮蔽旧观察能让成本减半，解题率不变（2508.21433）。

## 3. 目标

用 §1 同口径的数据，在同等规模的冲刺上验收：

| 指标 | 现状 | 4.2 目标 |
|---|---|---|
| worker 上下文峰值（中位） | 349K | ≤ 150K |
| 每小时主控轮询调用 | 约 560 | ≤ 60 |
| worker 起步到第一次平台调用的上下文 | 最高 44K | ≤ 15K |
| 以 `cd` 开头的 shell 调用 | 1,766/h | 降 70% |
| 临时 JSON 解析脚本 | 621/h | 降 80% |
| 压缩后重读压缩前文件的比例 | 16% | ≤ 5% |
| 压缩后重测已测 SHA 与级别 | 11 次 | 0（由账本拦截） |
| 已证伪方向被重试 | 未统计 | 可统计，且 ≤ 1 次/worker/天 |
| DeepSeek 提示缓存命中率 | 未统计 | 可见；主控与 worker 均 ≥ 80% |

## 4. 工作包

顺序按「每单位工作量能省下多少」排。A 必须先做，后面各项的效果都靠它衡量。

### A. 先测量（小）

1. 每次模型调用记录缓存命中与未命中 token（DeepSeek 的 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`，其他驱动取等价字段）。按 agent 和工具汇总，在协作页显示。
2. 参照 Reasonix 的 `CaptureShape`/`CompareShape`（`cache_shape.go`），给每次未命中标出原因：系统提示变了、工具表变了、压缩或截断。
3. 每个 MCP 工具记录返回字节数，统计每小时调用次数。
4. 压缩回放基准（见 §5）先做出来，用于比较新旧压缩方案。

### B. 变化驱动的等待，取代轮询（小到中）

1. 新增 `parhelion_wait(since=<rev>, until=[inbox|test|agent|judge], timeout)`：在服务端阻塞，没有变化时只返回 `{changed:false, rev}`，有变化时只返回 `rev` 之后的增量。
2. `parhelion_status(if_rev=...)` 在没有变化时返回 `not_modified`。
3. 服务端合并突发事件（参考 Reasonix：250ms 合并、每秒最多 32 条）。
4. 同一等待连续无变化时自动延长超时，并告诉模型它在等什么，避免空转。
5. `agent_wait`、`test_wait` 保留，内部改走同一条增量通道。

针对：每小时约 560 次轮询。

### C. 实验账本与由代码构建的压缩种子（中，收益最大）

1. **账本**：每个 worker 一个追加式 JSONL，放在 `results/ledger/<problem>/<worker>.jsonl`，修改以新行加 `supersedes` 表示。条目类型：`measurement`、`hypothesis`、`experiment`、`insight`、`failure`、`decision`、`constraint`。公共字段有 `id`、`claim`（≤240 字）、`why`、`scope`（用例/形状）、`sha`、`evidence`（测试运行 ID、回执 ID、路径锚点）、`confidence`（measured/inferred/speculative）、`revisit_if`。完整字段见调研 §5.3。
2. **平台自动写入**：每次测试完成写 `measurement` 和 `experiment`（逐例时间、相对基线、结果）；回执到达时按预测自动把对应假设标为 confirmed、refuted 或 inconclusive。
3. **模型写入**：`parhelion_note(type, claim, ...)`。`parhelion_submit_gate` 要求附 `hypothesis_id` 和 `predicted_effect`；没有就从 commit 说明自动生成一条。
4. **查询**：`parhelion_ledger(view=open|unexploited|failures|case:05|since:<id>)` 和 `parhelion_recall(query)`。后者检索账本、历次交接和归档会话。
5. **压缩种子由代码拼装**，目标 6–10K 字符，按下列顺序，最后一行是行动指令：
   - 固定规则（比赛规则、管理员指令、平台规则），原文照录；
   - 状态卡，扩展到全部用例的同代差距；
   - 账本摘要：全部未验证的假设、全部未利用的洞见、最近 15–20 条失败方向（每条一行，带 id），其余写成「另有 N 条，用 recall 查」；
   - 模型写的叙述，不超过 1,500 字，按固定标题校验：现在在哪、做到一半的事、未提交的改动、下一个实验的 id；
   - 原始尾部：最近几轮原文，以及 `git status`、`git diff --stat`；
   - 行动指令：取最高优先级的假设或洞见，说出它的 id，重新推导之前先 recall。这一句替换现在的「Do not re-read」。
6. **交接校验**：每个 open 状态的 id 都必须出现在种子里（由代码保证）。叙述中提到的 SHA、路径和测试运行必须真实存在。上一版叙述里有、新版漏掉的决定和失败自动补回。叙述校验失败一次就退回只用账本的种子。
7. **压缩时机**：在判题回执或阶段边界上压缩（没有进行中的工具调用，假设刚有结论），不再等到 349K。现有阈值保留为上限。
8. **修正 `_checkpoint`**：保留阶段结果的结尾而不是开头，上限按种子预算重新分配。

针对：忘记的优化点、重复的死路、16% 的重复读文件、11 次重复测试。

### D. 用平台视图取代临时脚本（中）

把 621 个脚本按用途聚类（初步看是逐例对比、两个 SHA 的差异、判题历史、队列、榜单和 tbest），对外提供 `parhelion_report(view=per_case|diff|history|queue|board, ...)`。逐例表固定列为：用例、本方 µs、tbest µs、差距 %、噪声带。`opsb queue list`、`opsb history` 能看到的内容，在 MCP 里都要能拿到。

针对：621 个脚本、约 100 次 CLI 绕行，以及 `sed`、`python3` 合计约 1.5MB 的输出。

### E. 统一的工具输出上限（中）

MCP 服务端只设一个出口 `bound_output()`：小结果直接返回；超过上限（建议 4–6KB）的落盘，返回路径、头尾预览和总字节数；分页工具按窗口返回；失败时保留尾部；回读落盘文件时不再二次落盘。`status`、`kb_query` 和测试摘要支持简洁与详细两种格式。

### F. 同伴消息协议（小到中）

1. `parhelion_squad` 改为结构化信封：`{refs:[账本 id], claim ≤280 字, evidence: 路径#锚点, ask?}`。
2. 正文超过 1,200 字的要么拒收，要么自动转成附件；与已有消息高度重复的引用会被剥掉。
3. 收件方只收到 id 和 claim，同时在自己的账本里记一条 `source=peer, confidence=unverified`。
4. 多条消息在下一个回合边界合并投递，不再逐条唤醒 agent。

针对：`peer` 371KB、`result` 723KB，以及 Codex 压缩后只剩同伴长消息的问题。

### G. worker 启动包（小）

第一条消息直接给出：

- 任务契约；
- 工作树的绝对路径；
- 1–2K token 的仓库地图，来自 `aoci.txt`，类似 Aider 的 repo map；
- 要改的 3–5 个文件及行号范围；
- 本题账本摘要。

工具接受显式 `workdir` 或绝对路径，worker 不再需要 `cd && cat`。主控能直接查到 worker 的文件、日志尾部和 diff 统计，不必自己 `cat`。

### H. 观测遮蔽与缓存稳定的前缀（视驱动而定）

1. 驱动支持清理工具结果时，对超过约 10 轮、可再生、且已记入账本的旧输出（shell、JSON、编译日志）做遮蔽，替换成 `[elided <tool> <bytes> sha256 path]`。保留最近约 10 轮、错误信息、账本和回执结果。分批遮蔽（`clear_at_least`），避免每次都让缓存失效。
2. 状态卡等易变内容放在消息末尾，不放进系统提示。工具表的字节和顺序保持固定。系统提示里不放时间戳。
3. LLM 摘要只用于把一个已完成的阶段整理成账本条目。

DSH、ACP 和 Codex app-server 是否支持清理工具结果，还没有核实。不支持的驱动只做 C 到 G，这几项都在平台可控的工具和回合策略内。

### I. 预算与护栏（小）

- 每个 agent 设工具调用和模型调用上限，以及未命中缓存的输入上限，参考 Antigravity SDK 的 `BudgetConfig`。
- 状态卡显示距下次压缩还有多少。
- 抑制相同调用的连续风暴和空操作回显。
- 主控提示中加入「按任务复杂度分配力度」。

### J. 渐进披露（小到中）

- 系统提示保持短小。比赛相关的操作手册改成按需加载的文档：元数据约 100 token，正文不超过 5K token，符合 Agent Skills 规范。
- `kb_query` 只返回 id 和一行摘要，正文用 `kb_get(id)` 取。
- 测量 MCP 工具表本身的 token 数；偏大时，把少用的工具放到代理或工具搜索后面。

### K. worker 边界（小，安全）

- worker 进程的 `PYTHONPATH`、工作目录和可读路径不应包含平台源码和凭据（`~/.parhelion` 下的会话、账号文件）。
- 需要的数据（排行榜、tbest、回执）全部通过 MCP 提供，例如 D 里的 `board` 视图。
- 检测到 worker 读取凭据文件时告警。

## 5. 验收方法

1. **回放基准**：用本次冲刺的 worker 会话，在每个压缩点切开，比较四种种子：
   - 现方案；
   - 现方案加账本摘要；
   - C 的完整方案；
   - 完整历史，作为上限。
   
   探针题从切点之后的会话里生成，例如「切点后尝试过的想法，切点前是否已经提过」「哪些死路在切点后又被重试」。各 worker 取 bootstrap 置信区间。C 必须先在回放中超过现方案，才上线。
2. **线上指标**：§3 的全部指标，再加重复实验率（相同 `diff_hash` 或相同 approach）、从种子到第一个新实验的 token 和时间、每轮测试周期的 shell 调用数、每题每次判题的得分增益。
3. **A/B**：各题预算相同，一半 worker 用新方案，另一半用旧方案。

## 6. 不做或暂缓

- 只用 LLM 摘要的压缩：调研显示它不比遮蔽好，而且更贵。
- 不计缓存代价地激进改写旧工具结果：会让前缀缓存反复失效。
- 训练压缩模型：成本高，收益不明。
- 把 Reasonix 的命中率宣传（94%、「便宜 30 倍」）当作预期：那是自报数字，工作负载也不同。Reasonix 已于 2026-11-12 停止维护，只作参考实现。
- 单纯调低压缩阈值：状态落盘之前，阈值只影响成本，挡不住遗忘。

## 7. 实施顺序

1. A（测量）、B（等待），同时做回放基准。
2. C 的第 6、8 项（交接校验、修正 checkpoint），以及 C 的第 2 项（平台自动写账本）。这几项改动最小，能立刻止住遗忘。
3. C 的其余部分、D、G，然后 E、F。
4. H、I、J 按测量结果决定。K 与第 1 步并行。

每一步都用 §3 的指标和 §5 的回放判断是否保留。
