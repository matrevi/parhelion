## 1. 方法学

### 1.1 窗口与分母

两份窗口，都从**同一批** `opsb replay metrics` 一次运行里取，口径不新造：

- **窗口 A（与 `reports/P13-bound-output.md` §4 逐字可比）**：默认窗口 `2026-11-25T14:30:56.914692+00:00 .. 2026-11-26T05:41:17.607328+00:00`，**15.172 小时**，`~/.parhelion/logs/sessions/mesh-dee-*.jsonl` **135 个** worker 会话日志。复现结果与 P13 完全一致：`parhelion_*` 调用 **2,782 次 / 7,810,115 B**。
- **窗口 B（与 §3 的 349K/150K 目标可比）**：P03 报告用的那 13 个 sprint worker 日志（`--sessions` 显式列表），峰值中位 **349,306 token**，与 P03 §2 逐字相同。

命令（只读；`--no-cost` 只为缩短运行）：

```text
PYTHONPATH=cli ~/.parhelion/venv/bin/python cli/opsb replay metrics --json --no-cost \
  --workspace ~/Competitions/mat-chem-sim-pred
```

**分母有两套，各用在该用的地方，都在本节写清**：

| 分母 | 数值 | 用途 |
|---|---|---|
| D1 平台 MCP 回复（`parhelion_*`） | 2,782 次 / 7,810,115 B | 与 P13 §4 对照；`bound_output` 的作用域 |
| D2 **全部**工具结果 | 22,141 次 / 56,144,556 B | H / I 的真正分母（`bound_output` 覆盖不到驱动内置工具） |

D2 的构成（窗口 A，按工具）：`bash` 16,904 次 / 40,531,499 B（72.2%）、`read` 1,041 / 6,808,322 B（12.1%）、平台 `parhelion_*` 2,782 / 7,810,115 B（13.9%）、其余（`job_output`、`edit`、`web_*`、`skill` 等）1,414 / 994,620 B。窗口 B（13 个 worker）的工具结果是 4,480 次 / 9,471,157 B。

**「轮」的定义**：计划写「超过约 10 轮」。本场 worker 的 `session/prompt`（平台下发的提示，`replay.loader` 的 `Turn`）**中位只有 3 个**（p90 6，max 57），所以「10 轮」若按提示数算几乎永不成立。本报告改用**模型步**（一次 `usage_update` = 一次模型调用，中位 120 步/agent）作窗口单位，另用「最后 20 次工具调用」做敏感性对照（结果差 <3%，见 §2.2）。这个选择在报告里明写，不隐式改口径。

### 1.2 token 系数（三处标定，不拍脑袋）

字节到 token 的换算用了三个互相独立的标定，结论一致，取 **0.33 token/字节（≈3.0 B/token）** 为主值：

1. **首次提示（schema 类文本）**：13 个 sprint worker 的原生 DSH 会话里，`system/message` 2,829 B + `request/header.tools` 27,911 B + brief 1,762 B = 32,502 B，对应首个 `assistant/message` 的提示 token **9,843** → **3.31 B/token（0.302 token/B）**。实测。
2. **工具结果（JSON/代码/数字）**：对「相邻两次模型调用的 Δused vs Δ工具结果字节」做带常数项的最小二乘。取 ΔB≥8 KB 的 1,552 对：`Δused = 678 + 0.368·ΔB`，R²=0.80；取全部 18,530 对（ΔB≥1 B）：`α=0.367`、常数 808、R²=0.61。两档给出 **0.356–0.368 token/B**。实测。
3. 仓库既有常数 `drivers/startup_pack.BYTES_PER_TOKEN = 3.6`（0.278 token/B）比 1、2 低约 15%。报告用 0.33，并在 §9 给出用 0.278 的敏感性（全部省量乘以 0.84）。

### 1.3 启发式与校验（哪些是启发式）

- **H 的「可再生」分类**是启发式：`bash` 命令按程序白名单（`cat`/`sed`/`grep`/`ls`/`git log|show|diff|…`/`python -c` 无写操作…）判「严格可再生 R1」，其余（构建、测试、`opsb`、`ssh`、`write`、重定向、`git commit`…）判「R2：要重跑才拿得到」，平台视图判「Q：可再查」，判题回执、账本、同伴消息、工具决策判「N：不可再生」。分类器是**规则**、不是模型；判据集中在脚本的 `bash_class` / `call_class`，可复核。误差方向：R1 偏保守（凡是带写入或未知程序一律不算可再生）。
- **P14 的「含结论」**是关键词正则（SHA、带单位的数字/分数、判定词），**启发式**。用 8 条自写字符串做过分类器自检：4/4 正例命中、0/4 负例误报；但这只是语法自检，**没有**在真实 result 上做人工标注（本包禁止把消息正文读进上下文），因此绝对值（94.4% / 85.6%）可信度中等，**两栏之差**（交叉表）可信度更高，报告以后者为主要依据。
- **I 的「空操作回显」**分两层：同参重发后**结果字节是否完全相同**（确定性，非启发式）与**前 300 字符是否重复**（启发式，作为「同一张表又打印了一遍」的下界）。
- 其余（工具表字节、kb 字段字节、总线消息长度、DSH 事件的 `compaction/*` 计数）都是**确定性实测**。

### 1.4 只读与隐私

会话日志、`~/.dsh/sessions/**`、真实比赛目录都只读打开；`agent_bus.db` 按 `replay/sources.py` 的 `sqlite3.connect("file:<db>?mode=ro", uri=True)` 打开，只做聚合统计。本报告与所有脚本**不含**消息正文、cookie、账号名、用户 ID、token；`kb_query` 只统计字段名与字节数，不读字段值。没有对真实比赛目录运行任何会写 `results/feedback-log.jsonl` / `.feedback-signatures.json` / `.candidate-archive.json` 的命令（未跑 `scheduler.cli_bridge status`，未用 `parhelion_report queue`）。仓库里没有真实设备值。

## 2. H 观测遮蔽

### 2.1 驱动是否支持清理或替换旧工具结果（逐个给结论与依据）

| 驱动 | 客户端可见的协议面 | 能否清理/替换旧工具结果 | 依据 |
|---|---|---|---|
| **DSH**（`dsh --profile acp`） | ACP stdio，方法只有 `session/{new,load,prompt,cancel,set_model,set_config_option,set_mode,list,fork,delete,resume,close,flush}`；服务端→客户端只有 `session/update` 与 `session/request_permission` | **不能**（平台侧没有接口）。DSH **自己**有 `@deepseek-ai/dsh-compaction-tool-result-pruner`（`thresholdChars: 8192`、`headChars: 4096`、`tailChars: 1024`，替换文本 `[... tool result middle pruned ...]`），但只在 `compactIfNeeded()` 的压缩流程里被调用（`context-overflow` 或达到压缩阈值时），不是每轮的前置闸门 | `drivers/dsh_driver.py`（`--profile acp`）、`drivers/antigravity_acp.py`（ACP 方法集）、DSH 包源码（`dsh-compaction-tool-result-pruner` / `compactIfNeeded`）、打包内 ACP 方法名清单 |
| **Antigravity ACP** | 同一个 ACP 客户端：`session/new`、`session/load`、`session/prompt`、`session/cancel`、`session/set_config_option`、`session/set_model`；系统提示经 `_meta.antigravity.systemPrompt.append` 注入 | **不能**：ACP 没有编辑历史的方法，config option 只有模型类 | `drivers/antigravity_acp.py` |
| **Codex app-server** | 客户端：`initialize`、`thread/start`、`thread/resume`、`thread/name/set`、`turn/start`、`turn/interrupt`、`thread/compact/start`；服务端：`turn/completed|failed|cancelled`、`item/started|completed`、`thread/tokenUsage/updated` | **不能**：只有整线程压缩（LLM 摘要），没有「按结果清理」的请求，也没有剪裁参数 | `drivers/codex_appserver.py`（`compact()` 只发 `thread/compact/start`） |
| **Claude**（`claude -p --input-format stream-json --output-format stream-json`） | 命令行为准：`-p`、两种 stream-json、`--permission-mode bypassPermissions`、`--setting-sources local`、`--strict-mcp-config`、`--mcp-config`、`--session-id/--resume` | **不能**：Anthropic 的 `clear_tool_uses_20250919` 是 Messages API 的参数，CLI 不暴露；Parhelion 与 CLI 对话，不直连 API | `drivers/claude_driver.py`；`docs/v4.2/research/token-economy.md` §3D |

**DSH 那一路还有实测旁证**：本机 942 个 DSH 原生会话里，`compaction/*` 事件（含 `prune`）只出现在 **8 个**会话中；**196 个 worker 工作树会话一次都没有**（`compaction/prune` 93 次、`compaction/start|end` 各 14、`compaction/summary` 13，全部在桌面版的项目根会话里，窗口内只有仓库根会话触发 33 次、释放 131,819 token）。也就是说：DSH 的剪裁器在本场**对 worker 从未生效**。

另外两条路也不通：**重写会话日志**——DSH 运行期以内存 surface 为准，日志是持久化快照，改日志不会改正在跑的上下文；且 4.2 守则把 `~/.dsh/sessions/**` 定为只读。**平台侧改写**——`bound_output`（P13）只作用于 MCP 回复（D2 的 13.9%），驱动内置的 `bash`/`read`（D2 的 84.3%）根本不经平台。

**结论**：H 的第 1 项（遮蔽旧工具结果）在现有四个驱动上**都做不到**，不是工作量问题，是没有接口。这不影响第 2 项（缓存稳定前缀：状态卡放末尾、工具表固定、系统提示不放时间戳）——那条是平台自己的提示与工具面，仍然可做，且与 J 重合。

### 2.2 遮蔽 10 步以前的可再生输出能省多少（估算）

方法：对每个 agent 按调用序给每条工具结果定位它所属的**模型步**（`bisect(usage_seqs, call.seq)`），若峰值时刻距该步已 ≥10 步则该结果可遮蔽；按 §1.3 的类别统计字节，再乘 0.33 token/字节。分母与窗口见 §1.1（两套都算）。只对 **R1/Q/R2** 报数，**N（判题回执、账本、同伴消息、模型自己的推理）不计入任何省量**。

窗口 A（135 日志，峰值中位 246,793 token）：

| 类别 | 结果字节 | 占全部工具字节 | 调用数 | 峰值时已 >10 步的字节 |
|---|---:|---:|---:|---:|

| R2 需重跑（构建、测试、`opsb`、`ssh`、写操作） | 23,066,490 | 41.1% | 12,376 | 20,814,160（90%） |
| Q 可再查的平台视图 | 6,345,624 | 11.3% | 1,430 | 5,757,976（91%） |
| N 不可再生（不计） | 2,439,572 | 4.3% | 2,756 | 1,770,109 |

按 agent 的「可遮蔽字节 → token ÷ 峰值」分布：

| 遮蔽范围 | 窗口 A 中位（p10–p90） | 遮蔽后峰值中位 | 窗口 B（13 worker）中位（p10–p90） | 遮蔽后峰值中位 |

### 2.3 旁证：DSH 自带剪裁器若在每轮生效

按 DSH 的规则（结果 >8,192 字符 → 保留前 4,096 + 标记 + 后 1,024）回放：

- 1,301 条结果（5.9% 的调用）超阈值，合计 21,802,978 B = **全部工具字节的 38.8%**；剪后剩 6,744,984 B，**省 15,057,994 B**（这些结果自身 −69%）。
- 折成峰值：**中位 −13.5%**（p90 −22.6%），13 个 sprint worker 上中位 −14.0%（p90 −24.8%）。

这条比「按年龄遮蔽 R1」小，但它是**驱动侧现成的、确定性的**手段，只要触发点从「压缩时」挪到「每轮」。本场它 0 次触发，纯粹是因为触发点在 DSH 的压缩流程里。

### 2.4 H 的建议与工作量

- **建议不做**（按计划里的原方案：平台去清理旧工具结果）。不是收益不够，是四个驱动都没有接口；硬做只能改 `~/.dsh` 里的 harness 配置，那会把平台策略变成用户全局设置，且 4.2 守则禁止。
- 如果将来某驱动开放了接口，按本报告 §2.2 的口径做 A/B：预期峰值中位 −22%（只遮 R1），实现量 2–3 天（含分页/回读路径与回归）。
- **可立刻做、且不需要驱动配合的替代**（都已并入 J 的建议）：降低**生产端**的工具输出（工具表、`kb_query` 载荷、`bound_output` 的既有上限），以及把状态卡从系统提示挪到末尾（H 第 2 项，平台侧可控）。

**(a) 同参重发（非相邻）**：509 次（2.30%），1,249,242 B。

**(b) 读同一文件的重复**：`read` 1,041 次；同一 `file_path` 第二次及以后 **567 次**，其中 **561 次返回了不同内容**（换了 offset/limit 或文件变了），只有 6 次完全相同；严格同一 `(path, offset, limit)` 只有 **8 次**（5 次内容相同）。所以「按路径抑制重读」几乎必然误伤——这与 P03 的「压缩后重读 19.6%」不矛盾：那是**跨压缩点**的重读（有账本可拦），这里是同会话内的顺序读取。

### 3.4 护栏值得做吗

不值得。三条理由，都有数字：

1. **可挡对象太少**：连续风暴 0.22%、同参重发 2.30%，其中真正没带来新信息的只有 0.76% 的调用、约 40 KB 回复字节（占 56.1 MB 的 0.07%）。
2. **误伤率高**：同参重发里 67% 返回了不同结果；`parhelion_status` 的同参重发 95/102 是新状态（护栏会挡掉状态刷新），`parhelion_test` 45/45 是新运行。按「参数相同就抑制」实现，**三次里错两次**。
3. **它想解决的问题已经被 B 拿走**：`status`/`test_wait`/`inbox`/`job_output` 的同参重发本质是轮询；4.2 B 的 `parhelion_wait(since=rev)` + `status(if_rev=…)` 已经让「不调用」成为正确做法（P03 实测主控轮询 136/h，P04 投影 91–67/h）。再加一层「同参抑制」只会和 B 打架。

### 3.5 预算（上限）值不值得做

- 设上限到 400：会挡住 **2/135** 的 agent（工具调用）、**1/135**（模型调用）；设 300 挡住 11/135 与 9/135；设 250 挡住 13/135 与 13/135；设 500 一个都挡不住。
- 本场没有失控 agent（p99 422，max 476），所以硬上限只在「真的失控」时有用，而那种情况下更该看的是**未命中缓存的输入上限**（窗口 A 的 135 个 worker 共 19,018 次模型调用，未命中输入合计 22.1M token，只占提示的 0.78%，缓存命中率中位 99.1%——未命中输入不是本场的问题）。
- **建议**：不设硬上限，只做状态卡上的「距下次压缩还有多少」（工具面已有的 `context_budget` 思路）；这是 S 级工作量（约 3 小时），且与 C 的压缩时机共用同一个读数。

## 5. P14 的 result claim（开头 280 字 vs 末段）

**口径**：`agent_bus.db` 只读，取 `kind='result'` 的 **370** 条；其中 **354** 条超过 `ATTACH_MAX=1200` 字符，是 P14 之后会被截成 claim 的那一批（另 16 条内联全文，不受影响）。按 `agents/peer.py` 的同一段代码重放：`claim = clip(body, 280)`（空白归一化后取前 279 字符 + `…`），末段 = 最后一个空行分隔块（无空行则最后一行）。正文长度中位 **2,193.5** 字符（p90 3,594），claim 只保留中位 **12.8%**；354/354 条的 claim 都以 `…` 截断，且都以正文第一行为开头。

**「含结论」= 含测得数字、SHA 或判定词**（启发式，判据见 §1.3）：

| 判据 | claim（开头 280 字） | 末段 |
|---|---:|---:|
| 含 SHA（7–40 位十六进制） | 263（74.3%） | 247（69.8%） |
| 含测得数字（带单位/百分比/分数/多位小数） | 189（53.4%） | 199（56.2%） |
| 含判定词 | 245（69.2%） | 228（64.4%） |
| **松散判据：三者任一** | **334（94.4%）** | **303（85.6%）** |

交叉表（松散判据）：

| | 末段有 | 末段无 |
|---|---:|---:|
| **claim 有** | 287 | 47 |
| **claim 无** | **16** | 4 |

严格判据（「测得数字 + 判定词」或「SHA + 测得数字」）下方向翻转但幅度很小：

| | 末段有 | 末段无 |
|---|---:|---:|
| **claim 有** | 97 | 72 |
| **claim 无** | **79** | 106 |

**读法**：

- 松散判据下 **claim 反而更强**（94.4% vs 85.6%，只有 16 条是「末段有结论、claim 没有」）；严格判据下末段略强（79 vs 72，净 +7 条 = 2.0%）。两种判据互相夹逼，**差异都很小**，没有任何一种支持「开头 280 字常常只是开场白」。
- 直接检验「开场白」假设：**354 条里的 152 条（42.9%）第一句不含任何结论标记**，但只有 **13 条（3.7%）**是「Here is …」「I will …」这类明确的元话术——第一句常常是标题/编号行，而不是寒暄。claim 中位覆盖 **2 句**，所以「第一句不是结论」并不等于「前 280 字没有结论」。
- 与 `ledger/checkpoint.py` 的经验**并不矛盾**：那是「长阶段结果被 `stage[:room]` 截断、结论在结尾」——同一个仓库里 `manager.worker_report` 保存 checkpoint 用的是 `summary.strip()[-4000:]`（**取尾**），而总线 result claim 用的是 `clip(text, 280)`（**取头**）。两条路径对「结论在哪」的假设是相反的；本场数据显示：**长结果两头都有结论，取头不吃亏，取尾也不占优**。

**建议与工作量**：

1. **不建议**改成「只取最后一段」：严格判据下净赚 2%，松散判据下净亏。**（不做，0）**
2. **建议**改成「开头 280 字 + 末段（截到 160–200 字符）」，或用一条明确的分隔（如正文最后一行以 `CONCLUSION:` 开头时优先用它）。交叉表显示这样能覆盖松散判据下 350/354（98.9%）、严格判据下 248/354（70%，对单取的 169/354 提升明显），总线字节代价约 +200 字符/条（全库约 +70 KB，即 P14 的 164,812 B 变成约 236 KB，仍是原 875,174 B 的 −73%）。**（做，S：约 0.5 h + 2 条测试）**
3. **可选**：给 `parhelion_agent_report(kind="result")` 增加 `claim` 参数（现在 `worker_report` 没有这个参数，result 的 claim 永远是 `derived_claim=True`），让 worker 自己给结论行；schema/handler/manager 三处 + daemon 路由，**（做，S：约 2 h）**。

## 7. NOTE（对 4.3 有价值、非显然的事实）

1. **DSH 已经有「观测遮蔽」，但触发点在压缩流程里。** `dsh-compaction-tool-result-pruner`（8,192/4,096/1,024 字符，标记 `[... tool result middle pruned ...]`）只在 `compactIfNeeded()` 里被调用；本机 942 个原生会话里 `compaction/*` 只出现在 8 个会话、**196 个 worker 工作树会话 0 次**。也就是说 4.2 H 想要的东西 harness 已经写好了，差的是「每轮也跑」和「按年龄而非仅按大小」。这是 4.3 里唯一能以小改动拿到 13–22% 峰值的地方，但需要 DSH 侧配合。
2. **「10 轮」这个单位在本仓不成立。** worker 的平台提示中位 3 个（p90 6），模型步中位 120 个。凡是要写「N 轮」的策略（H 的窗口、I 的连续风暴、状态卡的压缩提示）都必须先说明是「提示」「模型步」还是「工具调用」，否则差一个数量级。
3. **工具表就是起步上下文。** sprint worker 首次提示 9,843 token，其中工具表 27,911 B ≈ 8,432 token（86%），brief 只占 5%。「起步 ≤15K」这个目标对工具表而不是 brief 敏感；而平台切片从 sprint 的 8,322 B 涨到今天的 22,066 B（+165%），方向相反。
4. **同一个仓库里对「结论在哪」有两套相反的假设**：`manager.worker_report` 的 checkpoint 取 `summary.strip()[-4000:]`（取尾，注释写 "the end holds the conclusions"），`peer.result_envelope` 的 claim 取 `clip(text, 280)`（取头）。本场 354 条长结果两头都有结论，取头略优于取尾；两者应统一为「头 + 尾」。
5. **`kb_query` 的重复键在 brief 格式里被放大了。** full 载荷里重复占 27.4%，P13 的 brief 把条目压到 6 个字段后，重复占到 **48.3%**——压缩把正文压没了，把结构浪费留下了。这类「上限只管大小、不管内容」的漏点，值得在 P13 类改动里加一条「同一份数据是否挂两个键」的检查。
6. **「同参重发」在本仓是状态刷新的同义词，不是浪费。** `parhelion_status` 102 次同参重发里 95 次拿到新状态；`parhelion_test` 45 次全部是新运行。任何「参数相同就抑制」的护栏都会与 4.2 B 的变化驱动等待冲突。
7. **总线上的 result claim 只影响总控读到的部分，附件仍是全文。** P14 之后长 result 在总线上只留 claim + 路径（`<workspace state>/peer/<msg_id>.md`），所以 claim 的信息量决定「要不要去读附件」——这是 P14-2 的收益来源，也是为什么「claim 里带上末段」比「换个截断方向」更值。
8. **DSH 的压缩阈值在 1M 窗口上，worker 峰值 349K 够不着。** 这也是 H 的现状：不遮是因为没到 harness 的阈值，不是因为遮了没用。

## 9. 已知局限

1. **H 的省量是估算，不是实测。** 类别是规则启发式；token 由字节乘系数得到（0.33，实测三处标定在 0.278–0.368 之间）。用仓库常数 0.278 时全部省量乘 0.84（例如 R1 的 22.1% → 18.6%）。真正的实测要等某个驱动开放接口后做 A/B。
2. **`read` 归到 R1** 假设「文件没变就能重读得到同样内容」；本场 567 次同路径重读里 561 次内容不同，说明这个假设在**会话内**经常不成立，但在「遮蔽后需要时再读」的语义下仍然成立（遮蔽不删除能力）。若把 `read` 从 R1 剔除，R1 的字节量从 24.29 MB 降到 17.24 MB（占全部 30.7%），省量按比例降到约 15.7%。
3. **P14 的绝对值（94.4%/85.6%）是关键词启发式**，没有人工标注校验（本包禁止把正文读进上下文）；交叉表（16 vs 47、79 vs 72）是更可信的部分。分类器只用 8 条自写字符串做过语法自检（4/4、0/4）。
4. **Codex app-server / Claude / Antigravity 三路没有本场流量**（`~/.parhelion/logs/sessions/` 里只有 135 个 `mesh-dee-*` 与 1 个 `deepseek-*`），驱动能力结论来自代码与协议，**不是实测行为**；真机验证留给 4.3。
5. **J 的 kb 数字只覆盖 P13 之前的 full 格式**（40 次调用）；brief 格式的占比是按 `_compact_kb_result` 在同一批结果上重算的，不是线上实测。
6. **`mcp-calls.jsonl` 仍无数据**（P03 的计量在冲刺之后才合入），H/I/J 全部依赖会话日志这一路，没有与实时计量交叉验证。P13 报告 §7.7 预告的「用真实 `spilled`/`bound_bytes` 验证 §4 估算」本场仍做不到。
