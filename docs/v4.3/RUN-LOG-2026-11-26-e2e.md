## 发现的问题

1. **后台主控的 MCP 服务一启动就崩溃。**
   - 原因：4.2 K 的 worker 沙箱也套在了 `opsb driver launch ALL` 的后台任务上；MCP 服务作为 DSH 的子进程，继承了这份读禁。
   - 沙箱禁止 stat `~/.parhelion/sessions/`，`ensure_parhelion_migrated` 的 `mkdir(exist_ok=True)` 在目录已存在时仍抛 `FileExistsError`，于是任何在沙箱里运行的 `opsb mcp serve` 都起不来。
   - 4.2 之后还没有跑过真实冲刺，这条路径从来没有被执行过。
2. **主控在沙箱里也到不了守护进程。** 沙箱还禁读 `daemon.json`，`parhelion_sprint_start` 因此报「Start the Parhelion daemon」。managed worker 有 `relay.json` 里的限定 token，主控没有这条路由。
3. **修复：**
   - 沙箱内的进程看不到凭据存储，就跳过迁移，不再报错；
   - 只有全场主控（`ALL-10`）的后台启动不套 worker 沙箱，与 4.2 之前相同；单题 worker 照旧在沙箱里。
   - 两条回归测试：一条在真实沙箱里加载配置，一条检查只有主控免沙箱。去掉修复时两条都失败。
   - 后续（4.4）：给主控一个限定权限的守护进程 token，让主控也能回到沙箱里。
4. **主控照样传了 `enable_auto_submit: true`。** 提示里明确写了「不要传」，但主控的固定 brief 里有「Set enable_auto_submit=true when requested」。开关本来就是开的，所以没有任何变化；不过这说明这句固定提示会盖过用户的指示。
5. **旧席位被停后，新冲刺要靠 `replace` 才能开。** 主控自己发现并改用了 `replace`，多花两次调用。可以考虑让 `sprint_start` 的拦截理由直接附上「用 replace=[题] 开新席位」。
6. **已批准、却没人请求的候选永远不提交（4.3.1 修复）。**
   - 平台本该在验证完成 120 秒后代为请求，但它用 `(题, SHA, queued_at)` 精确匹配队列行与结果行来判断「本题有提交在途」。
   - 旧队列行的结果行带着另一种 `queued_at` 格式（例如 BodySliceExtract `e724a03`，11-24 入队），配不上，于是这一题永远被当成在途。
   - 本场 14 题里有 11 题因此卡住，worker 不主动请求的好候选只能停在 READY。
   - 现在改读同一次状态调用里队列视图的 `pending` 项。队列视图还会按 SHA 退役已有判题回执的行；在真实数据上，在途项为 0。
7. **取消了的测试还占着设备（4.3.1 修复）。**
   - 本机取消只杀本机 runner；设备主机上的启动进程被 init 收养，照样跑完 engine。没人在等的 final 运行（22 例 × 2 轮）因此占着 Die 0 好几分钟。
   - 14 个 worker 共用一张卡：等久了就取消重试，取消的旧运行留在队列里，队列越排越长。
   - 现在远端启动进程监视父进程，会话一断就结束 engine，broker 随之取消作业、释放设备。
8. **`parhelion_wait` 等满 60 秒就报「Request timed out」（共 32 次）。**
   - 托管的 DSH worker 对 MCP 请求的超时是 60 秒；4.2 按桌面插件的 120 秒设计，把阻塞上限定在 100 秒。worker 传 60–100 秒的 timeout，于是每次长等待都在 60.0 秒处断开，白白浪费一轮。
   - 修复：上限降到 50 秒，工具描述同步改为「max 50s」。
9. **`parhelion_note` 对已绑定的 worker 也报「the problem of this call is unknown」（8 次）。** 平台从总线查到了 worker 的题，但只拿来拒绝跨题调用，没有在 worker 不传 `problem` 时补上。修复：默认用 worker 自己的题。
   - 8、9 两条的进程都是 worker 启动时就加载好的（MCP 服务与守护进程），本场在跑的 worker 拿不到修复。冲刺中不重启，等新开席位或下次重启时生效。两者都只会多耗一次重试，不卡闭环。
