## 发现的问题

1. **后台主控的 MCP 服务一启动就崩溃。**
   - 原因：4.2 K 的 worker 沙箱也套在了 `opsb driver launch ALL` 的后台任务上；MCP 服务作为 DSH 的子进程，继承了这份读禁。
   - 沙箱禁止 stat `~/.parhelion/sessions/`，`ensure_parhelion_migrated` 的 `mkdir(exist_ok=True)` 在目录已存在时仍抛 `FileExistsError`，于是任何在沙箱里运行的 `opsb mcp serve` 都起不来。
   - 4.2 之后还没有跑过真实冲刺，这条路径从来没有被执行过。
2. **主控在沙箱里也到不了守护进程。** 沙箱还禁读 `daemon.json`，`parhelion_sprint_start` 因此报「Start the Parhelion daemon」。managed worker 有 `relay.json` 里的限定 token，主控没有这条路由。
3. **修复：**
   - 沙箱内的进程看不到凭据存储，就跳过迁移，不再报错；
   - 只有全场主控（`ALL-10`）的后台启动不套 worker 沙箱，与 4.2 之前相同；单题 worker 照旧在沙箱里。
   - 两条回归测试：一条在真实沙箱里加载配置，一条检查只有主控免沙箱。去掉修复时两条都失败。
   - 后续（4.4）：给主控一个限定权限的守护进程 token，让主控也能回到沙箱里。
4. **主控照样传了 `enable_auto_submit: true`。** 提示里明确写了「不要传」，但主控的固定 brief 里有「Set enable_auto_submit=true when requested」。开关本来就是开的，所以没有任何变化；不过这说明这句固定提示会盖过用户的指示。
5. **旧席位被停后，新冲刺要靠 `replace` 才能开。** 主控自己发现并改用了 `replace`，多花两次调用。可以考虑让 `sprint_start` 的拦截理由直接附上「用 replace=[题] 开新席位」。
6. **已批准、却没人请求的候选永远不提交（4.3.1 修复）。**
   - 平台本该在验证完成 120 秒后代为请求，但它用 `(题, SHA, queued_at)` 精确匹配队列行与结果行来判断「本题有提交在途」。
   - 旧队列行的结果行带着另一种 `queued_at` 格式（例如 BodySliceExtract `e724a03`，11-24 入队），配不上，于是这一题永远被当成在途。
   - 本场 14 题里有 11 题因此卡住，worker 不主动请求的好候选只能停在 READY。
   - 现在改读同一次状态调用里队列视图的 `pending` 项。队列视图还会按 SHA 退役已有判题回执的行；在真实数据上，在途项为 0。
7. **取消了的测试还占着设备（4.3.1 修复）。**
   - 本机取消只杀本机 runner；设备主机上的启动进程被 init 收养，照样跑完 engine。没人在等的 final 运行（22 例 × 2 轮）因此占着 Die 0 好几分钟。
   - 14 个 worker 共用一张卡：等久了就取消重试，取消的旧运行留在队列里，队列越排越长。
   - 现在远端启动进程监视父进程，会话一断就结束 engine，broker 随之取消作业、释放设备。
8. **`parhelion_wait` 等满 60 秒就报「Request timed out」（共 32 次）。**
   - 托管的 DSH worker 对 MCP 请求的超时是 60 秒；4.2 按桌面插件的 120 秒设计，把阻塞上限定在 100 秒。worker 传 60–100 秒的 timeout，于是每次长等待都在 60.0 秒处断开，白白浪费一轮。
   - 修复：上限降到 50 秒，工具描述同步改为「max 50s」。
9. **`parhelion_note` 对已绑定的 worker 也报「the problem of this call is unknown」（8 次）。** 平台从总线查到了 worker 的题，但只拿来拒绝跨题调用，没有在 worker 不传 `problem` 时补上。修复：默认用 worker 自己的题。
   - 8、9 两条的进程都是 worker 启动时就加载好的（MCP 服务与守护进程），本场在跑的 worker 拿不到修复。冲刺中不重启，等新开席位或下次重启时生效。两者都只会多耗一次重试，不卡闭环。
10. **主控因等待超时改用 bash 轮询，回应 worker 的延迟拉到分钟级。**
   - 这是问题 8 的连锁反应：主控的 MCP 服务是启动时加载的旧代码，拿不到 50 秒上限，于是不再用 `parhelion_wait`。
   - 此时 4 个 worker idle：两个在等主控决定（CGTensorProduct 要不要做 45–60 分钟的分块尝试；SgemmFp16Cube 在逃逸锁下要求 wa-repro 或「强制试探」，后者只有管理员能批，平台不会代为 force），两个没有在跑的任务。
   - 设备已不是瓶颈：起跑后 131 次测试，中位端到端 73 秒、p90 6.5 分钟，13 次取消；21:13 设备队列只有 5 个任务。
   - 处理：不重启主控（会丢 45 分钟上下文），只发一条平台通知；问题 8 的修复在下次开主控时生效。
11. **一颗 NPU 不够。** 第一轮最后 10 分钟 Die 0 的占用率是 100%（空闲 0%）。86 次设备运行里，等待中位数 22 秒、p90 345 秒，worker 累计等了 9948 秒；持锁中位只有 7 秒，瓶颈在排队。
   - 设备持锁时间里 99.6% 花在 ACL 主机侧（输入上传、输出回传与比对），真正执行内核的只占 0.4%。缩短主机侧准备是另一条提速路径，留作后续。
   - 处理：接入 `npu2`（见时间线 21:23）。应用的设备面板目前只显示主主机，`npu2` 上的活动在界面上看不到，留作后续。
12. **自动提交的门槛太低，交了很多没用的。**
   - 4.2.1 的低增益规则：低于噪声底线（1.9 分）但期望为正、P(gain>0) ≥ 0.5 的候选也批准为 EXPLORE。4.3.1 的平台代为请求又会请求所有已批准却没人请求的候选，于是每个这样的「抛硬币」都被交了出去。
   - 平台的 17 次代为请求里，13 次是 EXPLORE：期望增益 +0.03 到 +0.94，提升概率 0.50–0.65。已判的 12 发里 5 发刷新本题最好，合计只有 4.2 加权分；同期 worker 自己请求的 12 发贡献 27.2，probe 7 发贡献 34.7。
   - 估分整体偏乐观：NeighborListPbcFixedK 四次预测 +1 到 +2，结果都比最好分低 1.0–1.6；CGTensorProduct 预测 +24.6，实得 −4.4。置信度只有 0.45–0.66。
   - 处理：平台只代为请求 S2 干净过线（`ABOVE_NOISE_FLOOR` / `EXPECTED_IMPROVEMENT`）、熔断关闭的 exploit 候选；EXPLORE 由 worker 自己决定。经用户同意，`low_gain_min_prob` 调到 0.6。
13. **后台主控用 `create_goal` 等下一轮，结果进程退出。**
   - 后台（ACP）启动只发一次提示：回合结束时平台关闭 stdin，进程退出，会话记为 `completed`。DSH 的 `create_goal` 只在 DSH 自己的界面里续轮，ACP 下不会再有第二轮。
   - 第一轮的主控一直没有结束回合（靠 bash 轮询，见问题 10），所以没撞上；第二轮的提示禁止了 bash 轮询，主控改用 `create_goal`，日志最后一条就是 `end_turn`，没有报错。
   - 处理：本轮在重新拉起的目标里写明不要结束回合，循环调用 `parhelion_agent_wait` / `parhelion_wait`。
   - 后续：主控的固定 brief 要写明「后台会话一个回合就是整个生命期」；或者让 ACP 运行器在冲刺进行中、主控 `end_turn` 后自动追加一轮。
14. **`sprint_start` 把已换席的题报成「已停」。**
   - `replace=[题]` 停掉该题的全部席位，另开一个 `replace-N` 席位。之后按 `mode=solo` 调用（包括预览）时，平台按 `solo` 席位名去找，找到的是已停的旧行，于是报 `blocked: Worker explicitly stopped`，其实该题的替换 worker 在工作。
   - 风险：主控若照这个结果再 `replace` 一次，就会把正在工作的 worker 换掉。
   - 处理：请求的席位已停、而该题有更晚开的在线 `replace-N` 席位时，报 `existing`，附上在线席位与被替换的旧 agent。回归测试去掉修复时失败。修复在 `cli/opsb_core/agents/sprint.py`，跑在守护进程里，下次重启守护进程才生效。

15. **门禁开关被一次长时间的 bridge 运行改回旧值。**
   - `SchedulerEngine._save_state` 只写本进程改过的键：拿 `_raw_state`（上次读到或写入的磁盘内容）和内存里的配置比较。保存后 `_raw_state` 会更新为合并后的磁盘内容，但内存里的 `self.config` 没有更新。
   - 于是一个先读到 0.5 的进程，在别人设为 0.6 之后保存一次（这次正确保留 0.6），再保存第二次时，0.6 与内存里的 0.5 不同，被当成本进程的改动，写回 0.5。
   - 处理：保存后同时用合并后的配置刷新 `self.config`，与 overrides、held_items 一样。回归测试去掉修复时失败（`0.5 != 0.6`）。bridge 每次调用都是新进程，修复立即生效，无需重启。
16. **守护进程关闭时把所有在线席位标成「已停」。**
   - `stop_all` 把在线席位写成 `stopped`。这个状态表示管理员主动停席：跟进消息被拒，`sprint_start` 报 blocked。所以任何一次正常重启都会结束整场冲刺的所有 worker，而进程崩溃反倒留下可恢复的 `error`。
   - 处理：关闭时写 `error`，附「Daemon stopped; send a follow-up to resume this seat.」，与崩溃恢复一致。
17. **DSH 席位恢复后丢了 brief。**
   - DSH 的 ACP 没有 `session/load`，恢复时只能开新会话，而新会话只收到跟进消息本身，没有席位 brief。
   - 处理：适配器记下「请求了恢复但没能载入」，下一条提示前补上按原任务重建的席位 brief，并说明工作树、分支、账本和收件箱都没变。
18. **主控开出的额外 worker 没带题名。**
   - `dee-a1c141` 的 problem 是比赛名，工作树是比赛根目录，而不是 QuantScaleCalib 的仓库。已在主控目标里提醒它核对或重开。
   - 后续：`parhelion_agent_spawn` 在比赛级工作区要求题名，或拒绝不带题名的 worker 席位。

13 的补充：重新拉起的主控第二次仍在几分钟内结束回合，单靠提示写「不要结束回合」不够。现在由平台兜底：后台主控（ACP）回合结束时，只要冲刺里还有未停的席位，就追加一条继续提示，最多 120 轮；一轮不足 30 秒就先等满 30 秒，防止空转。
