# P29 估分排序校准

分支：`impl/P29-ranking`。在 P21 与 P23 合入后的 `main` 上开发：要用回放基准与 restore 定价。

## 为什么

**校准层决定的是「发哪一发」。** 上一场 74 次上台阶里，有 39 次（164.94 分，占 49.8%）带着桶级判决被选中。校准层不是涨分的原因，而是选择器（00-SUMMARY §3.2）。所以 4.3 要的是**排序更准**，不是把估分当闸门。

**问题出在跨代外推：**

| 测量 | 结论 |
|---|---|
| 同代重测（`est`） | 基本无偏 |
| 跨代改动（`d_hid`） | 高估约 3.7 倍（R3 §1.5） |
| 各题估分器的留一交叉验证 | 方向准确率中位 0.72，Spearman 0.28（00-SUMMARY §4.9） |

当前 `main` 的情况：
- `scheduler/estimator.py` 的同源抖动是常数 `SIGMA_HIDDEN_JITTER = 2.70`；
- 跨代预测没有饱和变换：判题分数函数在高分区天然饱和；
- 4.2.1 已经让低增益候选按低优先级放行，**优先级的准确度**因此变得更重要。

## 范围

### 1. σ 用实测值

估分器的同源抖动改为 `scheduler/judge_noise.sigma_for(title)`，按题取，不足时取全场合并值。仍取不到时回落到常数。

### 2. 两档预测

估分时，依据该 SHA 与基线之间的改动规模分档：
- **同代重测**：同一 SHA，或改动不触及内核源码；
- **跨代改动**：其余情况。

改动规模由 diff 判定，复用 `ledger/gitref.py` 的 `diff_hash`，或 `git diff --numstat`，限时、失败时按跨代处理。

跨代档的预测增益要经过饱和变换：
- 用判题公式把预测时间映射成分数，而不是线性放大本地比值；
- 再按本题回执上拟合的收缩系数缩小。

**拟合只用 as_of 之前的回执，不能用到未来数据。**

### 3. 排序质量指标

新模块 `scheduler/ranking.py`，在 P21 的回放上计算：

| 指标 | 定义 |
|---|---|
| Spearman | 同一时刻待发的候选之间，门禁优先级与实际判分增益的 Spearman |
| top-1 命中率 | 优先级最高的那一发实际刷新最高的比例 |
| 增益误差 | 预测增益与实际增益之差：中位、均值、分档统计 |

三项都给按 worker 或按题重采样的 bootstrap 置信区间。

**数据不够时如实写。** 一个时刻只有一个候选时，Spearman 无从计算。可以改用「门禁预测增益与实际增益」的逐发 Spearman，并在报告里说明口径。

### 4. 启用标准

与 P06 相同：
- 新排序在两场回放上的 Spearman 或 top-1 命中率，置信区间下界高于现方案，才默认开启。
- 否则开关 `ranking_v2` 默认关，只合入测量部分与 σ 替换。σ 替换本身也要在报告里给出回放对比。

### 5. 接入

`estimator.py` 只加薄接入点，新逻辑放进 `scheduler/ranking.py` 或单独的模块，不超过 350 行。

## 约束

- 只改优先级与预测，不新增任何暂缓理由。
- 额度不进入任何阈值。

## 复用

- `scheduler/receipt_predict.py`、`scheduler/predict_interval.py`、`scheduler/case_calibration.py`；
- `ScoreEstimator.discount_draw_to_contemporary`；
- P21 的回放框架；
- `cli/opsb_core/replay/score.py` 的 bootstrap 写法。

## 测试

- σ 的取值与回落；
- 分档判定；
- 饱和变换的单调性与边界；
- 拟合只用 as_of 之前的数据：用构造的未来回执验证不被读到；
- 指标计算。

## 验收

两场回放上，现方案与新方案的三项指标及置信区间，写进报告，并据此给出开关的默认值。
