## 4. 单发循环长什么样

11-10 的提交动作只有一种形态（根会话 149 次 `submit-queue` + 46 次 `submit-validated` + 41 次 `npu-test`，另有 4 次 `tools/cj submit`）：

```text
tools/submit-queue.py enqueue <Title> <sha7> "<一句人话的理由>"
tools/submit-queue.py run
```

`enqueue` 的第三个参数就是今天的 `--note`，而且**第一天的 note 就已经是"假设 + 数字 + 预期"**。ConcatD 在 03:33–04:02 的五连发是完整样本：

| 时刻 | note 原文（截断） | 结果 |
|---|---|---|
| 03:33 | `one DMA for all input pointers, 10 GM scalars in the prologue` | 52.36 |
| 03:53 | `prologue 10 GM scalars + one DMA for both arrays: int32_mid 6.80->4.96us` | 49.94 |
| 03:56 | `rollback: a458798 scored 49.94 < 52.36` | 48.41 |
| 03:59 | `retry: same source measured 52.36 / 48.41, hidden noise is +-4` | **0.00（WA）** |
| 04:02 | `restore after a single WA on the same source (platform flake?)` | 50.08 |

四件事在这一条链里全齐了：**写假设 → 变差就回滚 → 发现同源噪声 ±4 并主动重摇 → 判定"平台抽风"后恢复**。这不是后来才总结出来的方法论，11-10 03:56 的 note 里就有了。

## 6. 20 分钟的评分规则考古，是这一段最高杠杆的动作

`032fab64`（label：`Reverse-engineer the scoring rule`）11-10 09:04 开出、09:24 结束，567 条记录、0 次本地测试、7 次提交相关命令。它的推理轨迹按步留下了完整的发现顺序：

1. 先读仓库里已有的 CLI 与技能文档，再翻 `results/*/submissions.json` —— **发现逐例 `time` 与 `best_time` 都在里面**；
2. 打判题站的 `/api/problems/{id}/ranking`，确认 `testcases[]` 带 `tbest` 与 `type`，`baseline: None`；
3. 同一份源码两发的 `best_time` **逐字节相同**，而分数不同 → tbest 不随自己移动；
4. 翻全站排行榜约 3,250 行 / 36 页，发现 fastest 记录里有 **Wrong Answer** 提交比 `tbest` 还快 → 推断 `tbest` 只取 Pass；
5. `min(passing) < tbest` 在 50 个 cell 上 **0 次出现** → 坐实；
6. 找到元数据三件套：`score_mode: 1`、`use_baseline: false`、`iterations: 5`，以及 `ranking_submission_mode: 'latest'`；
7. 公开例 tbest 在 24 小时内一个 cell 都没动；`time` 量化到 1/3 → 3 次重复取均值；
8. 我们从未在任何公开例上追平或超过 tbest。

这八条后来全部进了 `results/scoring-rules.md`（"`latest` 计分 + 50 例等权 + 任一门失败整题清零 + tbest 只取 Pass + 同源重投重计时"），而 11-18 之后所有关于同代基线、噪声底、公开/隐藏剪刀差的判断都建立在这份文档上。**它是整场最高杠杆的 20 分钟。**

代价与边界说清楚：这一步靠的是**登录态会话文件**（会话里能看到的操作是读既有 session、拼请求头、翻页抓取；此处含凭据），也就是 4.2 工作包 K / P15 明确要从 worker 侧收掉的那条路。**这不是"应该放开凭据"，而是"这件事应该由平台来做"**——元数据本来就在平台的判题接口里。

## 8. 对 Parhelion 4.3 的建议（只写 DSH 段特有的，不重复 00-SUMMARY 的 Top 10）

1. **开局豁免要给到"该题首次有分"为止，不是固定 3 发。** 11-10 的 39 发里前 3 发只占 7.7%，而 9 题里有 4 题（CTC/Pad/LayerNorm/MML）在前 3 发内根本没找到可用版本；CTC 到第 40 小时才有分。4.3 的 `probe_allowance`（`gate.py` 的开局三发）方向对，窗口太窄。建议：题目 `current_score == 0` 时按"未出分"计，豁免到首次 Pass 或累计 N 发（N≈8–10，可配），只受额度与冷却约束。
2. **派活说明按"验一个假设"写，而不是按"优化这题"写。** 11-10 产出最密的两小时全是 `Multilabel 16-bit accumulator` 这种粒度。4.3 的 `SOLO_TASK` 是 315 字符通稿（见 00-SUMMARY §4.6），建议在 `mode=dual` 之外增加"假设席位"：一个席位 = 一个机制关键词 + 一个预期方向 + 一个判据。
3. **把"计分规则与 tbest 取证"做成平台首日任务。** 输入是判题接口的元数据（`score_mode`/`use_baseline`/`ranking_submission_mode`/`iterations` + 50 例的 `tbest` 与 `type`），输出是 `results/scoring-rules.md` 同构的文档，由平台生成、无需凭据落到 worker 手里。这是 11-10 单位时间产出最高的一件事，也是 4.3 目前唯一的"必须靠越界才能完成"的高杠杆动作。
4. **允许"知识波"席位：整段时间不产提交。** 11-11 一整天 0 提交换来的是后面 9 天的复用率。4.3 的每个席位都以"交候选"为唯一交付物（`SOLO_TASK` 要求 `parhelion_submit_gate`），没有"只产出 KB/文档/测量台"的合法形态。建议新增 `role=knowledge`（交付物是 `parhelion_kb_record` + 文档路径，KPI 不是分）。
5. **冷启动期允许更贵的本地验证。** 11-10 是 5.8 次本地测/发，后期 2 次/发。4.3 的 `level=standard` 若成为默认，冷启动期的单发周期会被本地验证拖长——建议按"该题是否已有线上分"在 `smoke`/`standard` 之间自动降级。
6. **同源重投从第一天就是常规动作（26%），门禁要能分辨意图。** 11-10 的 `retry: same source measured 52.36 / 48.41, hidden noise is ±4` 与 `restore after a single WA` 是两种完全不同的重投。4.3 目前一律按 `ALREADY_ACTIVE_ON_BOARD` 定 0 增益（见 00-SUMMARY §4.2/§4.9），会把恢复式重投也一起拦掉。
