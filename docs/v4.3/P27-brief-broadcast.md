# P27 派活情报与全队广播

分支：`impl/P27-brief-broadcast`。在 P26 合入后的 `main` 上开发（`drivers/brief.py` 冲突）。P22 已合入时用它的规则摘要；没合入时跳过那一行。

## 为什么

**派活说明。** 上一场 11-22、11-23 两天的 brief，中位长度分别为 1160 和 1285 字符，必含六项（R2 §1.2）：

1. 独占目录与分支；
2. 测试与提交命令；
3. 目标分与 Top1，以及加权空间；
4. 本题病根；
5. 汇报方式与收件人；
6. 停手条件。

当前 `main` 的 worker 契约（`drivers/brief.py`）已接近 1.5KB 上限，板面只有 `Board: score/status/rank`。状态卡与扩展状态卡有最好分、最近回执和差距，但没有榜首、加权空间、最近几发的机制，也没有停手条件。

**广播。** 上一场 11-23 有两类结果：
- 9 条全员广播，每条都在 20 分钟内改变了 3–5 道题的方向。最有价值的一次是主控对 10 题做横向扫描：本地内核体积对比线上公开例耗时，然后广播出去（R1 §3.4）。
- 但同一机制也闹出两次事故：本地 profiler 得出的「硬件规律」被当成事实广播出去，线上一发 −11.83（00-SUMMARY §4.8）。问题在于看板上没有字段区分「本地猜测」和「线上回执」。

当前的 `parhelion_squad` 只能定向发送，没有广播，也没有证据等级。单题诊断工具都是一题一查。

## 范围

### 1. 启动包与扩展状态卡的情报段

在 `drivers/startup_pack.py` 增加一段，数据由 `services/state_card_ext.py` 提供。**契约本身不加行。** 内容：

- **榜首与加权空间**：榜首分、本题在榜分、两者之差乘以难度权重。数据取自已有的精简榜单缓存，见 `brief.py` 里算 leader 的代码，不联网。
- **最近三发**：每一发的机制关键词（取账本假设的标题，或回执 note）、判分与是否新高。
- **当前假设与停手条件**：未关闭的假设 id；按 `ledger/budget.py` 的尝试预算，还剩几次；六发无增益的计数。
- **规则摘要**（P22 已合入时）：一行，写榜型与 σ̂。

整段受 `startup_pack` 的字节预算约束，超预算时按现有顺序收缩。这段的大小记进 MCP 计量，现有的 `tool=startup_pack` 已经在记。

### 2. 广播 `parhelion_squad(to="all")`

- 投递沿用 P14 的回合边界合并投递，对象是本工作区所有在跑席位，发送者自己除外。
- **频率限制**：worker 每 10 分钟最多 1 条全员广播，主控不限。超限时回复说明，不投递。
- 收件方的账本行沿用 P14 的 peer 行。

### 3. 证据等级

- squad 信封增加必填的 `evidence: {class, ref}`：
  - `class` 取 `local`、`paired`、`online_receipt` 之一；
  - `ref` 指向运行 ID 或 submission_id。
- `class` 不是 `online_receipt` 的消息：
  - 收件方正文前标「待验证」；
  - 协作页也显示「待验证」：Swift 用 decodeIfPresent 读一个可选字段；改动超过 30 行就只做后端，列为后续。
- 旧信封没有 evidence 时按 `local` 处理。
- P28 在知识库侧用同一组取值。

### 4. 跨题横向扫描 `parhelion_report(view=sweep, metric=…)`

- 只限主控。
- metric 可取 `size`、`compile`、`cold`、`pmu`。
- 每题一行，列出：
  - 在榜 SHA 与最新正式运行的该项指标；
  - 公开例的线上耗时，有回执时才列。
- 只读磁盘上已有的结果：`fast_feedback` 的 elf、cold3、pmu 卡，以及测试报告。不触发任何设备运行。
- 回复受 4KB 上限约束。

### 5. 指标

`cli/opsb_core/replay/sprint_metrics.py` 增加两项：
- 全员广播的条数；
- 带各证据等级的消息数。

会话日志与总线只读，只出聚合数字。

## 工具表余量（P26 审查后补充）
