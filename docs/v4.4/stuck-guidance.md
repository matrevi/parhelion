# 卡住时的引导：让能力弱的模型也能持续刷分（4.4 设计草案）

用户要求（2026-11-26）：能力较弱的模型（本场是 DSH）需要借助对硬件的理解、社区经验和以往的突破记录才能优化得又快又好；可是把这些读进来，会和上下文管理、工具数量冲突。要想清楚怎么在 worker 卡住时提供引导。

## 一、现状：知识有，送不到

本场第二轮（21:17–22:14 UTC，16 个 worker，4071 次工具调用）：

| 渠道 | 内容 | 实际使用 |
|---|---|---|
| 五元知识库 | 220 条：硬件规律约 90 条（15 条已验证、33 条反模式），tiling、向量化、异步流水等模式，56 条带线上回执证据；另有突破 48 个文件、社区 23 个、代码积木 25 个 | `parhelion_kb_query` 共 56 次，占 1.4%；有 2 个 worker 一次没查 |
| 门禁回复里的提示 | 按题名或机制关键词挑至多 2 条反模式或 Bug，≤600 字节 | 只在提交门禁时出现，此时方向早已定下 |
| 启动包 | 契约、工作树、仓库地图、要改文件、账本与情报、交接，约 6K token | 没有知识库段，也没有硬件段 |
| 停滞换席 | 每题 6 发实际扣额的判题没有提升，才换人 | 太晚：本地上的几十次无效迭代不计入 |

worker 的工具习惯：bash 占 40%，`read` 375 次，`parhelion_test_wait` 339 次（最常用的平台工具），`edit` 187 次。

卡住的形态（主控 21:34 的盘点）：加权差距最大的几题（FFT3DBatchComplex、QuantScaleCalib、EdgeIndexCoalesce、CGTensorProduct、SgemmFp16Cube）都卡在少数几个离群用例上，本地 100–8000 µs，榜首几 µs，差两到三个数量级。worker 却在做序言微调、调参这类只能挣几个百分点的改动。差两三个数量级的用例，靠微调永远追不上，要换算法或换执行单元。

所以问题不在知识库里缺什么，而在于：
1. **时机**：知识只在 worker 主动查询或提交门禁时出现，卡住的时候没人送。
2. **形态**：查询按关键词返回 3 条×600 字符的条目，worker 要自己判断哪条适用。弱模型最不擅长的正是这一步。
3. **尺度**：worker 看不出「这个用例差 800 倍」意味着什么，于是一直在错的尺度上优化。

## 二、原则

1. **平台判断卡住，平台选知识。** 卡住的检测与知识挑选都由代码确定性完成，可复现、可回放；模型只负责执行一个实验。
2. **一次只给一个实验。** 推送的是「引导卡」：一个假设、改一个变量、预期效果、证据出处、怎么判断成败，≤800 字节。不推条目列表。
3. **卷宗放磁盘，上下文里只放指针。** 完整资料写成工作树里的文件，worker 用它最熟的 `read` 按需读取；消息里只有卡片和文件路径。
4. **不加工具，走现有渠道。** 卡片附在 `parhelion_test_wait` 的返回里（最常用的工具），idle 时走收件箱跟进；卷宗用 `read`。
5. **逐级升级，越往上越贵。** 先确定性卡片，再换正交方向，再请强模型教练，最后才换席。
6. **每张卡都记账、可评估。** 卡片的采纳与结果回写到知识库证据，评估哪类卡真正有用。

## 三、设计

### 1. 卡住检测（P30）
守护进程每个 tick 用已有数据给每个席位打一个卡住类别（都不需要新埋点）：

| 类别 | 信号（阈值可配置） | 典型含义 |
|---|---|---|
| `build_loop` | 连续 3 次编译失败，或同一编译错误重复 | 卡在语法或接口上 |
| `wa_loop` | 同一用例连续 3 次 WA/RE | 数值或边界条件没想通 |
| `plateau` | 最近 8 次测量相对本地最好都在噪声带内，或 40 分钟没有新的本地最好 | 在错的尺度上微调 |
| `no_candidate` | 60 分钟没有可交候选 | 方向发散或卡在环境 |
| `scale_mismatch` | 加权差距的前 3 个用例与 tbest 相差 ≥50 倍，而最近改动都是 <10% 量级 | 需要换算法或执行单元 |
| `stagnation` | 现有的 6 发规则 | 线上确认无进展 |

数据来源：测试登记表（`test_runs/`）、账本、判题回执与门禁结论、逐例时间（已有 `state_card_ext` 的同代加速比与 tbest 差距）。

### 2. 题目卷宗（P31）
平台为每题生成 `<工作树>/.parhelion/dossier/`，全部由代码从已有数据拼出，题目状态变化时增量刷新：

- `index.md`（≤1 KB）：差距分诊结论与各文件的一句话说明。
- `gap.md`：差距分诊。逐例列出加权差距、与 tbest 的倍数、输入规模与形状特征，并按倍数分三档：
  - ≥50 倍：需要换算法或执行单元（例如把大规模矩阵乘从向量单元移到矩阵单元、把 O(N²) 换成排序或分桶）；
  - 3–50 倍：数据通路与 tiling（搬运合并、双缓冲、片上缓冲复用）；
  - <3 倍：微调（循环展开、同步合并、标量开销）。
  这一档是给弱模型最有用的一句话：告诉它该在哪个尺度上想问题。
- `hardware.md`：从已验证的硬件规律和反模式里，按本题机制标签挑出的 ≤10 条，每条带证据等级。
- `prior-art.md`：机制相同的其他题的突破（48 个突破文件）、社区方案和代码积木，按与本题差距档位的匹配度排序。
- `dead-ends.md`：本题账本里已证伪的方向，避免重走。
- `cards.md`：历次引导卡及其结果。

**机制标签**（P33）：每题一组机制标签（如 gather、reduction、矩阵乘、FFT、排序/分桶、逐元素），由强模型读题面一次性标注并经人工审核，存进工作区元数据。知识库条目已有类目，补上同一套标签后，挑选就从关键词匹配变成标签交集，结果确定且可解释。

### 3. 引导卡（P32）
检测到卡住时，平台按类别从卷宗里生成一张卡。下面是示意，数字与出处是编的：

```
[guide G-17 · plateau · FFT3DBatchComplex]
差距集中在 #03–#05（大 N，比 tbest 慢 300–800 倍），最近 9 次改动都在 ±3% 内。
假设：大 N 时按行做 DFT 是 O(N²)，改成基 2/4 分解可把这几例降两个数量级。
只改一处：给 N≥256 的分支换成分解实现，其余不动。
判定：#03 本地时间降到 1/10 以下算成立；变慢或 WA 就回退并在账本记 dead end。
出处：prior-art.md#2（RadialBasisBatch 同类分解，online_receipt），hardware.md#4。
```

- 送达：附在下一次 `parhelion_test_wait` 的返回里；worker idle 时走收件箱跟进。
- 同一席位同时只有一张有效卡，新卡取代旧卡。上下文压缩与交接种子只保留「卡号 + 状态」一行，卷宗不进种子。
- 采纳判定：worker 的下一条账本记录引用卡号，或下一次测试的改动命中卡片指出的文件或分支。

### 4. 逐级升级

| 级别 | 触发 | 内容 | 成本 |
|---|---|---|---|
| L1 | 首次检测到卡住 | 按卡住类别从卷宗生成的确定性卡片 | 0 |
| L2 | L1 后仍卡住（再 8 次测量或 30 分钟） | 正交方向：账本里没试过、标签匹配的另一类机制 | 0 |
| L3 | L2 后仍卡住，或 `scale_mismatch` 持续 | 强模型教练：用另一驱动（Claude/Codex）起一次只读会话，读卷宗、账本摘要与当前内核 diff，产出至多 3 张卡 | 每题每小时至多 1 次 |
| L4 | 现有停滞规则 | 换席，交接包含卷宗与卡片结果 | 已有 |

教练席复用现有的跨 Harness 派发（AGENTS.md 第 7 条）：只读、不提交、不改代码，产出写进 `cards.md`，由平台推送给原 worker。

### 5. 上下文与工具
- 上下文里新增的只有一张 ≤800 字节的卡和一个路径；卷宗读多少由 worker 决定，`read` 本来就是它的高频动作。
- 启动包加一段 ≤600 字节的「差距分诊」（取 `gap.md` 的结论），替换效果最差的仓库地图预算。
- `parhelion_kb_query` 保留给主动查询，不再是知识的唯一入口。
- 不新增 MCP 工具。若要主动求助，用 `parhelion_agent_report(kind=question)`，平台以 L1/L2 卡片作答，而不是转给主控。

### 6. 评估（P35）
- 指标：卡片送达到下一次本地新高的时间、采纳率、按卡片来源（L1/L2/L3、各卷宗文件）的增益、卡住时长占比。
- A/B：卡住事件按序号奇偶决定是否发卡，跑一场对比；同时用本场与上一场的会话日志回放，检验检测阈值是否在真实卡住处触发。
- 结果回写：带来线上新高的卡片，其出处条目在知识库里加一条 `online_receipt` 证据；连续无效的条目降权。

## 五、风险
- **误报**：阈值过敏会打断正常的长实验。卡片只是建议，worker 可以记一条理由忽略；同一类别 30 分钟内不重复发。
- **卡片质量**：L1 卡片完全由模板加数据拼成，可能空泛。用 P35 的采纳率与增益淘汰低效模板。
- **知识过时**：条目带证据等级与作废指针；卡片只引用已验证或带线上回执的条目，候选条目在卷宗里单独标「待验证」。
- **用词**：卷宗与卡片沿用知识库条目的通用术语（向量单元、矩阵单元、片上缓冲），不在平台文档里写厂商专有的编程接口名。

### 用户补充：知识大多是 agent 自己搜出来、测出来的

用户在实现过程中指出，worker 用到的知识不只来自平台提供的知识库，更多是它自己搜索、在设备上探测出来的。实现据此调整了三处：

1. 卷宗多一个 `findings.md`，排在硬件与先例之前：本题所有席位自己写进账本的未利用洞见、约束、未关闭假设和决定，标出来源（本人、队友）与置信度，队友的行一律标「待验证」。换席后的新 worker 也能读到前任的发现。
2. 卡片引用 worker 自己的线索：优先本人未关闭的假设，其次本人未利用的洞见，再次队友的洞见。只给账本引用号（如 `dee-6a9fc7/L-0060`），不转述原文：账本是自由文本，可能含任何接口名，而且转述占字节。
3. 知识库没有对应条目、也不清楚时间花在哪一段时，卡片给的是探测实验，而不是答案。例如 `scale_mismatch` 卡最后一行是「先探测：把这一段桩掉，测这个用例的时间分布，记成 insight」。卡片要求 worker 下一条账本记录引用卡号，测出来的结果就会回到 `findings.md`。

### 与设计的差异与取舍

- **分诊按判题公式算分值。**判题每例得分为 100/(1+ln(t/tbest)/ln1.5)，是对数尺度：一个慢 400 倍的用例提速 2 倍，只多不到 1 分；一个慢 2 倍的用例提速 2 倍，能多几十分。`gap.md` 逐例列出加权空间，以及提速 2 倍、10 倍、100 倍时的加权增益。每档另给「整档典型改动」的增益（默认算法档 10 倍、数据通路档 2 倍、微调档 1.3 倍，`guidance.tier_factors`）。聚焦档取增益最大的一档。以 FFT3DBatchComplex 为例，5 个慢 239–403 倍的用例占 155.6 分空间，但整档提速 2 倍只多 1.4 分，要 10–100 倍（+6.8 / +35.0）才划算；9 个慢 4–35 倍的用例整档提速 2 倍就有 +12.0。卡片因此写出数字，不只说「换算法」。
- **`scale_mismatch` 的条件。**设计写的是「前 3 个用例都 ≥50 倍」，实现改成前 3 个里至少有 `scale_min_outliers`（默认 1）个 ≥50 倍，同时最近 3 次计时改动的变化都 <10%。否则 CGTensorProduct、SgemmFp16Cube 这类只有一两个离群用例的题永远不会触发。
- **本地最好按基线分开记。**加速比相对不同基线 SHA 不可比较，所以本地最好按基线 SHA 分开记；基线换了（榜面动了）就算一次新的本地最好。
- **卡片只用模板与数据拼成。**卡片只引用已验证、且有线上回执的知识库条目，写成卷宗锚点（`prior-art.md#2 (Problem, online_receipt)`），不写条目原文，也不写条目 id。
- **卷宗引用知识库原文。**`hardware.md` 与 `prior-art.md` 原样引用知识库条目的标题与摘要，而现有知识库里有大量芯片与接口专名。平台自己写的文字都用通用词。用户 2026-11-26 决定卷宗原样引用知识库原文，`guidance.generic_terms`（专名到通用词的映射）保持为空，只作可选开关；仓库里不写这些专名。
- **启动包的「差距分诊」段尚未加**（§3.5），L2–L4 升级、P33 机制标签与 P35 评估也留到后续。

### 开关与阈值

`config.json` 的 `guidance` 段（默认值在 `config.DEFAULT_CONFIG`，只写一部分键时其余用默认）：`enabled` 控制检测与卷宗，`cards` 控制卡片送达（关掉后只检测、不推送），以及 §3.1 的各项阈值、`repeat_minutes`（30）、`inbox_after_sec`（600）、`outcome_window_minutes`（120）、`card_max_bytes`（800）。

## 七、P34 修订：文档侦察席（2026-11-26 用户提议，4.4.1 已实现）

用户提出：静态的平台知识库不够，应该有专门探索官方文档的 agent，把分析结果和指导交给刷题的 agent。这一节把原 L3「强模型教练」改成「文档侦察席」，尽量复用已有部件。

### 1. 已有部件

- 席位角色 `recon` 与 `knowledge`：只读，不跑测试、不提交（`mcp/tools.py` 的 `SUBROLE_DENIED`）；`knowledge` 能写知识库条目。
- 交付通道：`parhelion_squad` 带证据等级，队友的行进账本时标「待验证」，并出现在 `findings.md`；引导卡（P32）可以指向某一条发现。
- 卡住检测（P30）已经给出何时该问、问什么尺度的问题。

### 2. 新增：侦察席

1. **触发由平台决定。**同一题出现 `scale_mismatch`，或 L1 卡片送达后仍卡住（再 8 次测量或 30 分钟），平台开一次侦察。每题每小时至多一次。另外，worker 用 `parhelion_agent_report(kind=question)` 求助时也会触发，平台不再把这类问题转给主控。
2. **问题由代码拼成。**内容包括：卡住类别与信号；`gap.md` 里聚焦档的用例（倍数、加权增益）；当前候选相对基线的 diff 摘要（文件与函数名，不含整段代码）；`dead-ends.md` 里已经证伪的方向。问题按类别给出方向，例如 `scale_mismatch` 问「这种规模与形状的计算，官方推荐的算法或执行单元是什么」，`build_loop` 问「这个接口的约束和正确用法是什么」，`wa_loop` 问「这个数值或边界条件，官方怎么规定」。
3. **侦察席只读文档。**以本地文档镜像为主（部署配置登记的目录，由平台维护与刷新，可离线检索、可复现），镜像缺页时才联网。侦察席不接触设备，不改内核，不提交；工具与 `recon` 相同。驱动由主控从「可用 Harness」里选（见下面第 4 小节）。
4. **交付是结构化发现，至多 3 条。**每条包括：结论；文档出处（文档名与章节或页面地址）；适用条件；建议的单个实验（只改一处、预期效果、怎么判定）。发现写进本题侦察账本，来源为 `peer`，与其他发现同等对待，不另设证据等级；平台把排在最前的一条拼成引导卡推给原 worker，其余几条进 `findings.md`。
5. **回写。**worker 引用发现做实验，实验成立后由 `knowledge` 席写成知识库条目，文档出处作为条目证据之一；实验失败的，进 `dead-ends.md`，下一次侦察的问题里写明「已证伪」。
6. **缓存与预算。**问题按「题、类别、聚焦档用例、diff 指纹」做键缓存，同一个问题不重复侦察。每次侦察的 token 与耗时记进 `cards.jsonl`，供 P35 计算单位成本的增益。

### 3. 可用 Harness（用户勾选）

- 新增一个「可用 Harness」设置：每个驱动一个勾选框，存在 `config.json` 的 `agents.available_drivers`（驱动名列表）。主控开席位、派发外部 worker 与侦察席时，只能从勾选的驱动里选；`parhelion_harness_pool`、热帧的 `ready_drivers` 与 sprint/spawn 的校验都按这个列表过滤，没勾选的驱动直接拒绝并说明原因。
- 现有的 Claude 专用开关（`allow_claude_workers`）并入这个列表。
- 开发阶段默认只勾选 dsh，其他驱动关闭。

### 4. 需要改的地方

- 卡片来源多一种 `scout`；`cards.md` 与 P35 的指标按来源分开统计 L1 模板卡与侦察卡。
- `sprint.py` 的席位规格加 `scout`（角色等同于 `recon`，任务文本不同），由平台而不是主控开席；默认关闭，用 `guidance.scout.enabled` 打开。
- 本地文档镜像：部署配置登记目录（`guidance.scout.docs_dir`），侦察席只读；镜像的刷新是一个平台命令，不交给 worker。
- 侦察与刷题分开计量：侦察席的驱动和 token 单独记账，驱动熔断与暂停规则照旧适用。

### 6. 实现（4.4.1）

- 可用 Harness：`cli/opsb_core/drivers/availability.py`，配置项 `agents.available_drivers`。这个键缺省时，除 Claude 外所有驱动可用（4.3 行为）；部署配置已经写成只开 `deepseek`。`spawn_agent`、`parhelion_harness_pool`、热帧 `ready_drivers` 与 `start_sprint` 都按它过滤；`opsb driver available [--set ...]`；设置 › 驱动每行一个「可用」勾选框；doctor 的每一行带 `available` 字段。
- 侦察请求：`cli/opsb_core/guidance/scout.py`。守护进程的卡住引导 tick 判断是否需要侦察：`scale_mismatch`，或卡片送达 30 分钟后仍未采纳、仍卡住；每题每小时至多一次，同一问题只问一次。需要时给主控发一条 strategic 消息 `scout_request`，写明可用 Harness 与调用 `parhelion_sprint_start(problems=[...], role="scout", driver=...)`，由主控选驱动；`guidance.scout.auto_spawn` 打开后平台自己调用。问题由代码拼成，写进 `<state>/guidance/scouts.jsonl`，并进入侦察席的 brief。
- 侦察席：角色 `scout` 的工具与 `recon` 相同，另外不能用 `parhelion_submit_gate`；契约要求先读本地镜像、至多 3 条 `parhelion_note` insight。同一题已有在线侦察席时，新问题作为跟进消息发给它，不另开席。侦察席的工作树也会生成卷宗。
- 回答：侦察席在请求之后写下的 insight 或 constraint，进入 `findings.md` 最前面的「Doc scout findings」一节，并给卡住的席位生成一张 `scout` 卡，卡上只写引用号。有效的 scout 卡不会被卡住类别的新卡取代。
- 本地文档镜像：`opsb docs status | add <路径> | fetch <网址>`，目录取 `guidance.scout.docs_dir`，没设时用 `<PARHELION_HOME>/docs-mirror`。仓库不写具体文档来源；镜像目前为空。
- 测试：`cli/tests/test_guidance_scout.py`（8 个）。
